# 1장. Introduction and setup

### 1. RDBMS vs NoSQL

#### RDBS

- 데이터 구조/정리 : 정규화 장려
- 확장성 : 수직방향 확장 but, 한계가 있음
- 스키마 : 엄격한 스키마 규칙(읽기 요청에 강제됨)
- 무결성 제약조건 : 관계와 제약으로 강제 이행됨
- 스토리지/컴퓨팅 최적화 : storage 효율성 증대 / CPU 효율성 저하
- 읽기 일관성 : 강력한 일관성 + Replica는 최종적
- ACID : 준수
- 쿼리 언어 : SQL

#### NoSQL

- 데이터 구조/정리 : 비정규화 장려
- 확장성 : 수평방향 확장
- 스키마 : 유연한 스키마 규칙
- 무결성 제약조건 : 데이터 베이스에 따라 다름
- 스토리지/컴퓨팅 최적화 : CPU 효율성 증대 / storage 효율성 저하
- 읽기 일관성 : DDB는 강한 일관성/최종적 일관성 모두 지원
- ACID : DB마다 다르지만 DDB는 제한적 지원
- 쿼리 언어 : DB마다 다름

---
**- RDBMS가 설계될 당시에는 Storage가 중요한 제약요소였음**  
-> CPU 연산 효율성을 희생하더라도 스토리지 효율성을 챙기는 흐름

**- 현재는 기술의 발전으로 오히려 Storage가 값싸짐**  
-> CPU 연산 효율성을 챙기고 스토리지 효율성을 희생하는 흐름

### 2. DDB Case Study

#### 2-1) 아마존 리테일

- RDBMS에서 확장성, 일관성을 위한 제약조건 에러 발생 -> NOSQL 전환 필요성 증대
- 이때 수행되는 쿼리의 70%가 키, 값 형태였음
- 대규모 행사 시스템 확장으 ㄹ위한 계획 수립의 시간을 90% 가까이 절감
- 아마존 프라임데이 기간 동안은 초당 1억 2600만건 처리함

#### 2-2) 디즈니+

- 유저 이벤트(시청할 예정 목록 추가, 일시정지 후 다시 시청 등의 활동) -> DDB에 저장
- 글로벌 테이블(여러 지역에 걸쳐 데이터를 관리할 수 있도록 하는 기능) : 여러 API들이 데이터가 저장된 같은 지역 내에서 데이터를 읽고 쓸 수 있도록 구성됨

# 2장. AWS 관리 콘솔 및 SDK

## API를 활용한 연결의 장점
- 요청을 적절한 저장 노드로 전달
- 인증 및 권한 부여를 관리
- 시점 복구 나 읽기/쓰기 용량 설정 같은 추가적인 기능과 연동
- 질의가 올바른 형식으로 작성되었는지 확인


## 연결 방식
- AWS Console
- AWS SDK로 App 내 통신
- AWS Lambda <-> DDB 연동
- Local DDB (Docker 이미지)

## 요금 부과 방식

### 읽기 처리
- DDB가 읽은 데이터 양을 가장 가까운 4KB(1RCU)단위로 올림함.
- 읽기 요청의 일관성(최종적 일관성은 강력한 일관성 읽기의 절반)
- ex) 1KB -> 4KB(1RCU/ 최종적 일관성의 경우 0.5RCU)
- ex) 10KB -> 12KB(3RCU/ 최종적 일관성의 경우 1.5RCU)

### 쓰기 처리
- 1KB당 1WCU
- 가장 가까운 1KB 단위로 반올림함
- ex) 250 바이트 -> 1KB(1WCU)
- ex) 1.35KB -> 2KB(2WCU)

## Note
- item 은 RDBMS의 row에 해당
- 필수 항목은 파티션 키
- 파티션 키는 물리적인 저장 위치를 결정 -> 내부 해시 함수에 저장해 어떤 파티션에 저장될지를 결정
- 파티션 키는 Unique 해야 함. 만약 정렬키도 같이 설정되어있으면 (파티션 키, 정렬 키) 복합키가 Unique 해야 함.
- Console 내의 순서 != SDK로 반환되는 순서(오직 정렬키만이 순서 정렬)
